缓存击穿：100 个并发请求同时打数据库

发布于 2026-09-29 · 作者 林墨

缓存击穿是缓存击穿（cache stampede）的简称：某个热点键在过期的瞬间， 成百上千个并发请求同时发现「未命中」，然后一起去执行同一个昂贵的查询， 把数据库或下游服务打垮。

为什么会发生

最典型的场景是秒杀商品的库存缓存。假设缓存 TTL 是 60 秒：

// t = 60.000s，缓存刚好过期
// 此刻 1000 个请求同时到达
if (cache.get('stock:sku-1') === null) {   // 全部未命中
    $stock = $db->query('SELECT stock FROM ...');  // 1000 次相同查询
    cache.set('stock:sku-1', $stock, 60);
}

关键点在于：从「缓存过期」到「第一个请求把新值写回」之间存在时间窗口。 窗口通常是几十毫秒，但足以让上百个请求挤进来。

压测数据：某电商大促期间，单个商品缓存过期瞬间，数据库 QPS 从 200 飙到 18000， 数据库连接池瞬间打满，排队长度超过 3 秒。

三种解法对比

方案实现成本效果缺点
永不过期 + 后台更新高彻底消除击穿数据可能长期陈旧
逻辑过期中无感击穿实现复杂，需处理脏读
互斥锁重建低有效缓解锁失效时仍可能穿透

互斥锁重建：加上随机抖动

最实用的方案是互斥锁。实现有三个容易踩的坑：

  1. 锁必须原子创建。用 fopen($path, 'x') 而不是 file_exists() 后再 fopen()，后者在并发下必然失效。
  2. 锁要加随机抖动。不加抖动的话，同批写入的锁会在同一毫秒到期， 形成「锁惊群」——一万个请求同时发现锁消失，同时抢锁。默认 ±20% 随机化即可打散。
  3. 锁必须有兜底过期。持锁进程崩溃后锁不会自动释放， 必须设置 TTL，否则该键永久无法重建。

完整实现可以看 MornRain Cache Forge 的 StampedeLock 类。第三方库可参考 Redis 分布式锁文档。

降级策略不能省

等待锁的过程中，如果超过阈值仍没拿到锁，不要返回错误。 宁可返回一份略微陈旧的数据，也不要让用户看到 503。

小结

  • 用 fopen('x') 保证加锁原子性
  • 锁 TTL 附加 ±20% 随机抖动，避免锁惊群
  • 校验令牌才能释放锁，避免误删他人持有的锁
  • 拿不到锁时降级返回陈旧数据，而非报错
  • 回调抛异常时务必在 finally 中释放锁
